# PR 가이드

혼자 개발하는 개인 저장소 기준이다. **하루 작업을 주제 브랜치에 모아 `develop` 대상 PR 하나로 반영하고,
그날의 상세 내용은 PR 본문에 적는다.** 브랜치·커밋 규칙은 [Git 규칙](git-rule.md)을 따른다.

> 검토자가 없으므로 승인 절차는 없고 본인이 머지한다. PR은 리뷰를 받기 위한 것이 아니라,
> **변경 이유와 실행 확인 결과를 공개된 한 곳에 남기기 위한 기록**이다.

## 1. 왜 PR로 반영하나

`develop`에 직접 커밋해도 코드는 똑같이 반영된다. 그런데도 PR을 거치는 이유는 산출물 때문이다.

| 남는 것 | 쓸모 |
| --- | --- |
| PR 페이지(제목·본문·커밋·변경 파일·스크린샷) | 변경 이유와 검증 결과가 한 URL에 모인다 |
| 히스토리의 머지 커밋 | 하루 단위 작업 묶음이 이력에 드러난다 |
| 커밋 → PR 역추적 | 특정 커밋이 어떤 맥락에서 나왔는지 따라갈 수 있다 |

작업 기록(Notion)에는 상세 내용을 다시 쓰지 않고 **PR 링크와 그날 배운 것만** 남긴다.

## 2. PR 단위

- **하루 = PR 하나**가 기본이다.
- 제목에는 **날짜가 아니라 그날의 주제**를 쓴다. `2026-11-27 작업`처럼 적으면 목록에서 무엇을 한 PR인지
  보이지 않아 기록의 값이 사라진다.
- 하루 작업이 서로 **정말 무관하고** 둘 다 분량이 있을 때만 PR을 나눈다. 애매하면 하나로 묶는다.
- 커밋은 주제별로 나눠 둔다. PR이 하루로 묶여도 커밋 단위는 유지되므로 되돌리기와 본문 작성이 쉬워진다.

## 3. 진행 순서

```bash
# 1) 최신 develop에서 브랜치 생성
git switch develop && git pull --ff-only origin develop
git switch -c fix/chat-message-delivery

# 2) 작업하고 주제별로 커밋
git commit

# 3) push
git push -u origin fix/chat-message-delivery

# 4) PR 생성 (본문은 파일로 작성해 넘기면 편하다)
gh pr create --base develop \
  --title "채팅 메시지 전달·노출 문제 수정 (11/27)" \
  --body-file pr.md

# 5) 셀프 머지 — merge commit 방식, 원격 브랜치 삭제
gh pr merge --merge --delete-branch

# 6) 로컬 최신화
git switch develop && git pull --ff-only origin develop
```

GitHub 화면에서 만들 때는 **Pull requests → New pull request**에서 `base: develop ← compare: {작업 브랜치}`를
선택한다. **Squash and merge와 Rebase and merge는 사용하지 않는다.**

PR을 만들기 전에 diff를 한 번 확인한다. 의도하지 않은 파일이나 비밀 정보(토큰·비밀번호·`.env`)가 섞이지
않았는지 본다.

```
git diff --stat origin/develop...HEAD
```

## 4. 본문 양식

해당하지 않는 항목은 `없음`으로 적는다. 작업이 여러 개면 `## 작업 내용` 아래를 소제목으로 나누고
커밋 해시를 달아 둔다.

```markdown
## 작업 내용

### {작업 1 제목} ({커밋 해시})
- 
- 

### {작업 2 제목} ({커밋 해시})
- 

## 실행 확인
- 확인 방법:
- 확인 결과:

## 영향
- 영향을 받는 기존 기능:
- 설정·DB 변경 또는 추가 실행 절차:

## 화면 또는 실행 결과
- 스크린샷, 로그 또는 영상 (없으면 "없음")
```

**실행 확인은 실제로 확인한 것만 적는다.** 확인하지 못한 항목은 확인하지 못했다고 명시한다.
코드만 읽고 판단한 내용과 직접 실행해 본 내용을 구분해서 적는다.

### 작성 예시

```markdown
## 작업 내용

### 종료된 상담의 안읽은 메시지를 채팅 위젯에서 볼 수 있도록 수정 (a3f59c2)
- 열린 방이 없으면 종료 상담 최신 1건을 조회해, 안읽은 메시지가 남아 있을 때만 표시 대상으로 잡음
- 보여줄 때는 소켓 연결 없이 메시지만 한 번 불러오고 그 자리에서 읽음 처리
- 배지 기준을 종료 상담까지 포함하도록 확장

### REST 전송 실시간 전달 및 읽음 처리 범위 축소 (e90bdab)
- ChatMessageSentEvent 추가, sendMessage가 커밋 후 발행하고 핸들러가 전달
- 소켓 핸들러의 직접 전달 호출 제거(중복 전달 방지)
- 전달에 성공한 메시지 1건만 읽음 처리

## 실행 확인
- 확인 방법:
  1. 회원 패널을 닫은 채 관리자가 답변 후 종료 → 회원으로 로그인해 배지·패널 확인
  2. 회원 패널을 연 채 관리자가 REST로 전송 → 즉시 표시되는지 확인
  3. 전달된 적 없는 메시지가 다른 메시지 전달로 읽음 처리되는지 DB 확인
- 확인 결과:
  - 배지 2 → 패널에 답변·종료 안내 표시 → IS_READ=1 → 배지 0 → 다시 열면 새 상담 화면
  - REST 전송 메시지가 열린 패널에 즉시 표시, 중복 수신 없음(1건)
  - 전달되지 않은 메시지의 IS_READ 유지
  - 회귀: 접속 시점 읽음처리, 양방향 전달, 종료 실시간 반영 정상
  - lint / build / compileJava 통과

## 영향
- 영향을 받는 기존 기능: 회원 채팅 위젯, 관리자 상담 화면, 메시지 저장·전달 경로 전체
- 설정·DB 변경 또는 추가 실행 절차: 없음

## 화면 또는 실행 결과
- 패널에 종료 안내가 표시된 화면, REST 전송이 실시간 수신된 화면
```

## 5. 머지 후

- 최신 `develop`을 받아 동작을 한 번 확인한다. 문제가 있으면 다음 PR로 수정한다.
- 작업 기록(Notion)에 **PR 링크 · 그날 배운 것 · 다음에 할 일**을 남긴다. 상세 내용은 PR 본문에 있으므로
  다시 적지 않는다.
- 작업 브랜치는 삭제한다([Git 규칙](git-rule.md) 4절).

## 6. main으로 보내는 PR

`develop`에 쌓인 변경을 한 번에 확인하고 안정 버전으로 올릴 때만 쓴다.

| 상황 | base | compare |
| --- | --- | --- |
| 동작 확인 끝난 변경을 안정 버전에 반영 | `main` | `develop` |
| 배포 버전의 긴급 오류 수정 | `main` | `fix/{주제}` |
| 긴급 수정을 develop에도 반영 | `develop` | 같은 `fix/{주제}` |

`main` 대상 PR에도 같은 본문 양식을 쓴다. 긴급 수정에는 해당 오류 해결에 필요한 변경만 포함한다.
